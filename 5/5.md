Вопрос 1.
хотя в моей работе получилось все равно 2 миллиона(возможно из за умных оптимизаций и починок процесса библиотекой threading) вот как могло бы получиться меньше 2 миллионов
Пусть shared_counter = 100. Оба потока хотят сделать +1.

Поток 1:

    Читает shared_counter из ОЗУ в регистр → в регистре 100.

    Увеличивает регистр → 101.

    Тут планировщик Windows прерывает Поток 1 (Context Switch). Регистр с значением 101 сохраняется в память как контекст потока. Поток 1 «заморожен».

Поток 2 (пока Поток 1 спит):

    Читает shared_counter из ОЗУ → 100 (Поток 1 ещё не записал!).

    Увеличивает регистр → 101.

    Записывает регистр в ОЗУ → в памяти 101.

Поток 1 возвращается:

    Восстанавливает свой регистр из контекста → 101.

    Записывает регистр в ОЗУ → 101 поверх 101.

Итог: было 100, оба потока сделали по инкременту, а в памяти — 101, а не 102. Один инкремент потерян.

Что было в регистрах CPU Потока 1 в момент прерывания: уже увеличенное значение 101, которое ещё не попало в ОЗУ.  Oно потом затрёт результат Потока 2.

2. Что делает lock на аппаратном уровне

Процессор захватывает кэш-линию с переменной в эксклюзивное владение (по протоколу когерентности MESI). 
Остальные ядра, обращающиеся к этой же линии, блокируются и ждут. 
Операция «чтение → изменение → запись» выполняется неделимо — никто не может вклиниться. 

3. Почему с lock медленнее

Сериализация: ядра выстраиваются в очередь, параллелизм исчезает — фактически код становится последовательным.
Cache line ping-pong: два ядра постоянно «перетягивают» одну кэш-линию друг у друга, каждый lock требует межъядерных переговоров — сотни тактов.
Срыв конвейера: lock заставляет сбросить store-буфер и дождаться записи в память, ломая out-of-order исполнение.
Инвалидация кэшей: после записи одного ядра кэш другого помечается invalid, следующее чтение идёт в память.
