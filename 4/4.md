Вопрос 1.
хотя в моей работе получилось все равно 2 миллиона(возможно из за умных оптимизаций и починок процесса библиотекой threading) вот как могло бы получиться меньше 2 миллионов
Пусть shared_counter = 100. Оба потока хотят сделать +1.

Поток 1:

    Читает shared_counter из ОЗУ в регистр → в регистре 100.

    Увеличивает регистр → 101.

    Тут планировщик Windows прерывает Поток 1 (Context Switch). Регистр с значением 101 сохраняется в память как контекст потока. Поток 1 «заморожен».

Поток 2 (пока Поток 1 спит):

    Читает shared_counter из ОЗУ → 100 (Поток 1 ещё не записал!).

    Увеличивает регистр → 101.

    Записывает регистр в ОЗУ → в памяти 101.

Поток 1 возвращается:

    Восстанавливает свой регистр из контекста → 101.

    Записывает регистр в ОЗУ → 101 поверх 101.

Итог: было 100, оба потока сделали по инкременту, а в памяти — 101, а не 102. Один инкремент потерян.

Что было в регистрах CPU Потока 1 в момент прерывания: уже увеличенное значение 101, которое ещё не попало в ОЗУ. 
Именно оно потом затрёт результат Потока 2.


Вопрос 2. Решение через threading.Lock()

Исправленный код:
python

import threading
import time

shared_counter = 0
STEPS = 1000000
lock = threading.Lock()

def worker():
    global shared_counter
    for _ in range(STEPS):
        with lock:              # захват мьютекса
            shared_counter += 1
        # lock автоматически освобождается при выходе из with

print("Запуск двух потоков с синхронизацией...")
start_time = time.time()

t1 = threading.Thread(target=worker)
t2 = threading.Thread(target=worker)

t1.start()
t2.start()
t1.join()
t2.join()

print(f"Все потоки завершили работу за {time.time() - start_time:.4f} сек.")
print(f"Ожидаемый результат: {STEPS * 2}")
print(f"Фактический результат в памяти ОЗУ: {shared_counter}")

Результат: всегда ровно 2 000 000.

Почему с Lock программа работает в несколько раз медленнее:

    Сериализация. Мьютекс пропускает в критическую секцию только один поток. Второй блокируется и ждёт освобождения. Фактически потоки выполняются последовательно, а не параллельно — теряется весь смысл многопоточности для этой задачи.

    Накладные расходы на захват/освобождение. Каждый acquire/release — это системный вызов или атомарная операция с проверкой состояния. На 2 000 000 итераций это миллионы лишних действий.

    Context Switch. Когда поток не может захватить занятый мьютекс, ОС переключает контекст на другой поток — а это дорого (сохранение/восстановление регистров, работа планировщика).

    Потеря кэш-локальности. Потоки постоянно «прыгают» между ядрами и сбрасывают кэши друг друга.
